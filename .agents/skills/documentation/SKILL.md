# 项目文档

## 判断必要性

- 先读取项目 AGENTS.md，确认授权范围、文档入口和目录约定。Skill 不扩大任务授权。
- 明确读者及其要解决的问题；优先更新已有文档，只有独立、持续的读者需求才值得新增文件。
- 临时分析、计划、交接、任务进度、个人部署和一次性验证结果留在会话或项目外临时目录。
- 不因内容由 Agent 创建就删除；正式发布历史、来源、许可证、安全说明和维护规范有持续价值。

## 按读者需求组织

采用 [Diátaxis](https://diataxis.fr/start-here/) 的四类内容。每篇有一个主要目的，通过链接关联其他类型；不要强制套模板或为分类创建空目录。

| 类型 | 目的 | 应提供的内容 |
| --- | --- | --- |
| 教程 | 首次学习并完成实践 | 前提、连续步骤、可观察的预期结果、完成确认 |
| 操作指南 | 完成具体任务 | 适用条件、步骤、成功判断、必要的失败处理 |
| 参考资料 | 查询准确事实 | 参数、类型、默认值、单位、限制、错误语义及简短示例 |
| 架构解释 | 理解机制与取舍 | 职责、边界、数据流、故障行为、设计原因 |

短 README 可以保留概览和最小入门过程；详细操作、完整接口和架构说明通过链接展开。混合长文按有效内容的用途提取合并，不留旧路径空壳。

## 核对事实

- 从当前实现、类型、manifest、命令入口及 CI 核对契约，不把其他文档或代码注释当成最终证据。
- 区分运行事实、设计约束与未核实事项；无法核实的能力不能写成已支持。
- 检查默认值、环境变量、数据路径、权限门禁、故障和恢复语义。示例必须使用可用接口，不用新章节给旧示例打补丁。
- 同一事实指定主要维护位置，其他文档引用它；代码链接优先使用稳定文件路径，避免易漂移的行号。
- 发布记录中的日期、版本和已确认变更可以保留；产品行为文档不记录某次构建或测试通过数量。

## 写作

遵循 [Google 技术写作要点](https://developers.google.com/style/highlights) 和 [长期有效的文档原则](https://developers.google.com/style/timeless-documentation)：

- 直接描述行为，使用主动语态和明确主语；条件放在动作之前。
- 一段一个主要意思；步骤用编号，非顺序项目用无序列表；字段比较用表格。
- 标题和链接说明读者能找到什么。代码、参数、路径使用代码格式；图片提供有意义的替代文字。
- 产品文档描述已实现行为，不依赖“本轮、此前讨论、阶段 1、任务 A、即将推出”等会话背景。
- 正常操作步骤和产品生命周期阶段允许编号；不能靠关键词匹配决定删除。
- 保留实际限制和失败处理，不用“测试通过”替代能力边界，也不写无证据的可靠性、性能或兼容承诺。
- 保持所在文档的语言和术语一致；未经授权不进行整库翻译。

## 审查与交付

完整阅读即将修改的文档，逐份决定保留、改写、合并或删除。移动和删除前查找 Markdown 链接、纯文本路径、命令、源码注释及其他调用方；同时更新导航、相对路径、图片和锚点。

按任务要求检查链接、示例、事实一致性及改动范围。不要新增审查报告文件、会话总结、归档目录或关键词门禁。将处置结果与实际完成的验证在会话中说明。
