# 项目脚本与测试

## 确定用途和授权

- 读取项目 AGENTS.md，检查任务是否授权新增永久工具。Skill 本身不授权发布、部署、修改外部服务或清理数据。
- 优先复用现有入口。仅当持续维护任务需要重复执行或需要确定性自动化时新增正式工具。
- 一次性诊断、任务执行记录和个人环境工具放项目外临时目录；不因脚本来自 Agent 或使用临时输出目录就判定其无价值。

## 选择归属

| 用途 | 归属 |
| --- | --- |
| 构建、打包、资源生成 | 项目构建工具目录 |
| 版本同步、发布、产物上传 | 项目发布工具目录 |
| 容器入口、健康检查 | 项目运行工具目录 |
| 可重复静态检查 | 项目检查工具目录 |
| 有断言的功能或浏览器验收 | 测试目录 |
| 可重复性能测量 | 基准目录 |
| 仅服务单个包的工具或测试 | 该包内 |

目录遵循项目约定，不为不存在的用途建立空目录。可重复测试的运行产物遵循项目测试目录约定，不纳入版本管理。

## 编写执行契约

- 完整阅读即将修改的脚本及其调用方。明确入口、输入、输出、所需依赖、退出码、生成产物和副作用。
- 命令参数或环境变量承载可变配置；路径相对脚本或明确的项目根解析，不依赖个人工作目录、服务器地址或会话任务编号。
- 测试服务地址和端口允许通过参数配置或由测试分配；正式运行默认端口由产品契约决定，不机械删除。
- 失败返回非零退出码，不吞错误或输出虚假的成功结果；异步工作必须等待完成。
- 临时服务和文件明确所有权并在退出时清理，不删除非本次创建的资源；日志不输出凭据。
- 新增工具的用途和入口写进现有开发文档或入口帮助，不另建实施记录。

## 移动、删除和交付

- 删除前确认持续用途、替代入口和调用关系；没有引用只是证据之一。
- 移动时核对相对 import、工作目录、项目根、测试夹具、生成位置、文件权限和执行入口。
- 同步更新 package 命令、CI、Docker、发布配置、文档及其他脚本引用，不保留旧路径转发器。
- 按授权执行相关格式、链接、入口及行为检查；发布和生产操作必须遵循项目授权。
- 在会话中报告处置理由、实际验证和未验证事项，不新增脚本清理报告或交付记录。

## 测试维护

### 新增准入

写入测试前，按一组相关测试在会话或既有 PR 中简述以下判断，不新增永久 ROI 报告、评分表或审批流程：

1. **具体风险**：依据需求、源码或真实缺陷，指出哪种错误行为会损害用户或公开契约，以及断言如何暴露它；不是“改了代码所以补测”。
2. **覆盖缺口**：读现有断言、输入、异步次序和 mock 边界，确认缺的证据。优先复用或扩展既有用例，不能凭文件名、同名场景或框架名称判断重复。
3. **新增价值**：选择能充分暴露目标故障的最小范围，说明它比已有证据多证明了什么；不是机械选择最低层或最便宜的单测。现有覆盖足够时不新增是正常结果。

不为每个页面、每次修改、覆盖率、用例数或金字塔/奖杯的固定比例补齐测试。取舍同时考虑可暴露的真实故障、运行成本、夹具复杂度、维护和失败归因成本，不虚构收益数字。ROI 判断不授权删除既有测试、缩减回归或取消设计规范要求的验收。

### 归属与层级选择

- 按主要验证的责任归属：包和插件放自己的 `tests/`，工具放 `scripts/tests/`，跨模块流程放根 `tests/`。使用 `unit/`、`integration/`、`browser/` 按层级区分，再按实际子系统分组；只创建需要的目录。
- 入口命名 `<对象或行为>.test.ts`，采用连字符，不重复 `.unit`、`.integration`、`.browser` 后缀，不使用任务编号或含义模糊的 final/new/v2。单个文件围绕相关行为，不限制行数。
- `unit/` 不启动数据库、服务、子进程或浏览器；真实本地资源放 `integration/`，真实页面和组件交互放 `browser/`。需要外部服务、凭据或人工准备的验收放根 `tests/manual/`，不使用自动发现后缀。
- 同一风险可以有不同层的证据：规则分类、页面接线和真实持久化不是重复证明。保留必要异常路径；合并或删除须在授权范围内指出失效原因或实际接替的断言，不以文件名、关键词、长度或数量决定。

| 需要证明的边界 | 选择已有入口 | 不可冒称的证据 |
| --- | --- | --- |
| 可独立执行的业务校验、规则分类和数据转换 | 正常导入生产模块的 `unit/` | 不证明事件绑定、页面恢复或真实资源行为 |
| 真实 handler、协议适配或本地资源协作 | 对应 `integration/`，只启动目标所需资源 | 不要求每个集成测试都启动数据库，也不证明 UI 接线 |
| DOM 事件、提交/取消、快捷键业务效果、路由和异步生命周期 | 现有组件夹具或构建页面的 `browser/` | mock API 页面不证明实际后端鉴权、持久化或提供商行为 |
| 跨前后端、进程或重启的关键业务流程 | 已维护的真实链路验收 | 组件或 API 单独通过不能替代端到端证据 |

- 仅当输入差异属于纯计算或分类，且不改变 DOM 接线、异步次序、恢复或交互行为时，才把矩阵放在较小范围验证；浏览器保留交互后果不同的代表场景。未知结果、已接受操作、刷新恢复不能因文案相似合并，不为下沉测试强拆生产架构。
- 共享组件的公开业务行为集中覆盖，页面验证特有的 props、事件、上下文和插件接线；这不是“共享组件只准一个用例”。不重测供应商内部算法，但允许验证真实第三方集成的业务契约；不把待验证的行为本身 mock 掉。
- 业务测试不以源码字符串、私有变量名、无关 DOM/CSS 结构或巨大快照锁住实现。禁止截取源码函数执行或复制生产算法计算预期值；架构约束检查实际语法和作用域，不锁定缩进、注释、图标路径等无关细节，不扩大豁免。
- 前端展示边界遵循 [UI 设计规范](../../../packages/ui/docs/INDUSTRIAL_DESIGN_SYSTEM.md) §8.1：不新增 CSS、尺寸、响应式布局、动画、焦点、译文或展示格式的自动断言，也不把这些断言搬到 `unit/`。role、label 可定位控件，不把文案冻结为不可变契约。展示事项仍须按规范完成真实浏览器、错误检查和截图验收；无需为每次审查新增永久用例。

### 夹具、执行与失败处理

- 创建、等待、清理、fake 和 stub 放 `helpers/`；被系统加载的输入、示例插件、故障 worker、组件宿主放 `fixtures/`。导入辅助代码不得启动资源。先局部使用，确有跨模块复用再放根辅助目录；辅助代码自身的测试另放对应层级。
- 小型输入就地声明；重复使用或必须保留字节的数据才保存为夹具。入口之间不得相互导入，生产代码不得依赖测试。快照放对应目录 `__snapshots__/`；截图、日志、数据库、性能结果放项目外，不提交。保留夹具必要来源和许可证，不新增会话式 README。
- 先设置临时路径，再导入捕获路径的模块；结束时关闭资源、恢复环境和删除拥有的临时文件。服务使用分配的端口，明确进程身份和退出确认；超时、启动或清理失败必须报错。
- mock 用于受控边界，不能替换目标行为；夹具校验请求的方法、路径及相关参数，对非预期请求报错，不宽泛返回成功。第三方隔离按明确的 origin/path 在请求前提供受控响应，不在错误收集器里宽泛忽略失败；产品自身资源及未预期请求仍须报错，视觉审查使用符合视觉契约的受控资源。
- 将语言、时区、存储和数据作为显式输入，案例间隔离上下文；不是把所有案例固定成英文或同一时区。这些条件本身是被测输入时允许变化，不能通过换掉触发条件掩盖竞态。
- 根 `test` 构建后依次执行 fast、integration、browser，分类入口按目录筛选。单独执行前完成初次构建，相关产物变化后重新构建。性能测量独立；不得擅自缩减默认范围、添加跳过、重试、额外运行器或门禁。
- `test:plan --base <ref>` 只输出范围；`test:affected --base <ref>` 自行构建并执行完整快速测试和按模块选中的集成、浏览器测试。核对累计差异、工作区新文件及删除/重命名两端，不用扩展名或 Bun `--changed` 代替模块规则。新模块、跨模块依赖和共享夹具调用方须同步维护选择规则及用例；未知归属回退全量，读取失败返回错误。
- CI 使用一份提交范围计划，每个平台构建一次，通过独立工作区执行串行类别和原生浏览器分片；核对实际执行文件并集及提交、代码树和平台身份。任务失败、取消、异常跳过或证据缺失不得放行；按范围结果不能充当发布所需的同树双平台全量证明。
- 页面测试读取当前构建产物，组件夹具使用已有 Vite 配置和私有缓存；文件内复用服务/浏览器，案例间隔离上下文，不跨文件共享可变资源。用真实响应、组件状态或布局完成条件替代准备阶段的固定等待，保留真实时间边界和代表性截图，关闭失败必须报错。
- 使用有截止条件的状态/响应断言、自动等待及受控事件或 Promise gate；正常等待不是重跑测试。保留首次失败的脱敏证据，允许有目的地复现、对比基线及修复后复验，并说明条件变化与实际范围；不得用后续通过覆盖首次失败、加固定等待凑过、吞掉未知错误或重跑到绿。
- 搬迁时核对源码路径、动态 URL、资源路径、发现规则、类型检查、构建、CI、Docker和文档。确认测试与夹具不进入发布产物，辅助目录与手动验收不被自动发现，不保留旧路径转发器。

### 社区依据与适用边界

以下资料用于选择证据和权衡成本，不规定项目测试配比、工具栈、视觉策略或 CI 门禁；目录、命令和验收以项目契约为准。

- [Kent C. Dodds：测试数量与集成取舍](https://kentcdodds.com/blog/write-tests)：关注信心与维护收益，不为覆盖率补无逻辑测试；文中的覆盖率示意不是阈值。
- [Kent C. Dodds：避免测试实现细节](https://kentcdodds.com/blog/testing-implementation-details)：私有实现断言会在正常重构时误报，也可能漏掉事件接线错误。
- [Testing Library：指导原则](https://testing-library.com/docs/guiding-principles/)：从用户使用方式验证 DOM，不以组件内部实例代替行为。
- [Playwright：最佳实践](https://playwright.dev/docs/best-practices)：隔离案例与不可控第三方依赖，采用语义定位和有界等待。
- [Cypress：测试类型取舍](https://docs.cypress.io/app/core-concepts/testing-types)：组件、API 与端到端测试分别证明不同边界，不能相互冒充。
- [Martin Fowler：测试形状讨论](https://martinfowler.com/articles/2021-test-shapes.html)：清晰边界、快速可靠和有用的失败优先于类型比例。
